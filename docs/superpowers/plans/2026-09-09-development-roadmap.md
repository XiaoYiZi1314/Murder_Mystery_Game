# 十三雾｜八个开发周期总览

版本：2026-09-09。状态：开发规划，尚未执行各周期的真实业务实现。

**目标：** 在现有Next.js前端基础上，将[设计文档](../../设计文档.md) v1.0的一期需求完成为可运行、可记账、可审计、可恢复的单店PWA。采用 **8个内部开发周期**，每期有独立交付及验收门槛；正式上线仍要求一期全部功能完成。

**拆分依据：** 业务依赖和可验收闭环。将场次预约与押金履约拆开，避免状态/资金规则挤在一期；员工权限、审计和事件基础提前；站内通知随业务逐期交付；最后统一完成PWA、真实浏览器验收与部署恢复。

**范围约束：** 单店、自研Next.js全栈；不接在线支付，不做多商户、超时自动取消、顾客代登录、礼品电商或妆造租赁。短信/邮箱、小程序和运行时COS媒体迁移保留扩展点，不纳入本次一期；COS备份必须在C8完成。

## 1. 阅读与执行顺序

1. 本总览：明确当前起点、周期顺序和统一退出条件。
2. [共享协议](2026-09-09-shared-contracts.md)：所有周期共同使用的API、权限、数据、账本和事件边界。
3. [待冻结决策](2026-09-09-decisions.md)：只在对应周期开始前确认会影响实现的规则，不自行填默认业务政策。
4. 对应周期文档：按 `Cn-Tn` 工作包实现，以 `AC-Cn-nn` 验收编号留证据。
5. [需求覆盖矩阵](2026-09-09-requirement-matrix.md)：逐项回查源需求、页面、API及跨期职责，防止遗漏。

各周期的接口/文件路径标注“拟新增”表示未来要实现；示例测试为实施后的验证模板，本轮没有执行这些业务接口，也没有完成这些功能。

源文档说明由个人开发，未给明确截止日，因此采用工作包与验收门槛推进，不虚构固定周数。若需要日历排期，应在C1环境验证及D01–D07澄清后，按实际投入时间估算；C4/C5/C8是主要风险段，不能靠压缩验证时间赶进度。

## 5. 每期统一完成标准

- [ ] **真实业务：** 页面读取/写入真实服务并能刷新后保持；正常、空态、加载、失败、重复提交均可演示，交付路径不回退演示数据。
- [ ] **契约与迁移：** 服务遵守共享ID/金额/API规范；数据库迁移、约束和必需索引明确；已有真实数据不reset，回退/恢复路径可说明。
- [ ] **权限与隐私：** 后台逐接口授权；本人资源隔离；敏感操作留痕；举报私有数据不进入普通响应、日志、通知或公共缓存。
- [ ] **一致性：** 坑位、余额、积分、押金和结算以数据库事务/条件更新/唯一业务键保护；幂等重放与并发竞争有可复现证据。
- [ ] **业务事件：** 本期通知、审计与缓存失效随业务交付；消费者实际运行，失败能恢复，不能只写未被消费的事件函数。
- [ ] **组件复用：** 优先使用现有组件，可扩展时通过props/variant/className扩展；页面专属逻辑放features，共用样式进既有规范；新增组件同步设计预览。
- [ ] **验证证据：** 本期AC全通过，保存真实接口/数据库断言、关键浏览器交互、构建及已有回归结果；不能仅以HTTP 200或编译成功替代业务验收。
- [ ] **文档交接：** 更新API类型、AGENTS受影响规则、冻结决策、覆盖矩阵的实现/验收状态，列明未通过项及下一期输入。

建议按 `docs/verification/cycle-0n.md` 保存各期证据（拟新增），至少包含应用版本、迁移版本、测试环境、命令及结果、截图路径、AC编号和未通过项。计划中的待办仅在真实完成后勾选，本轮保持未勾选。

## 6. 关键交接与风险控制

| 交接点 | 必须提供的事实 | 防止的遗漏/错误 |
| --- | --- | --- |
| C1→全部 | Actor/权限、审计、幂等、事件协议、运行中的基础消费者 | 后期每个业务单独造认证、通知或日志 |
| C2→C3/C6 | 可用内容ID、关联和媒体读取策略 | 用fixture标识写真实报名，举报截图被公开 |
| C3→C4 | 场次/报名/申请状态分开，原子人数、审批唯一性 | 满员自动锁车、申请和报名混为一表 |
| C4→C5 | 已结束候选、报名、押金明确动作、共用journal | 把finished当settled、漏结/重复结、另建押金账 |
| C5→C6/C7 | 有储值历史/当前积分资格、真实账本及权益 | 评价门槛错误、现金消费漏积分、财务重复统计 |
| C3–C7→C8 | 所有事件实际投递、私有资源及页面矩阵、可追溯数据 | 只做首页离线、跨账号缓存泄漏、Push遗漏/重复 |

人工登记的风险由待结算提醒、服务端校验、留痕更正和逐笔对账共同降低；不承诺系统消除线下漏记。押金规则与权益在首笔真实履约前冻结；财务报表不能在账本口径不明时开发成看似完整的数字页。

## 7. 一期上线门槛

8期全部AC通过后，才能认定源一期开发范围完成。最终须验证：一条真实“注册→预约→押金锁车→履约→消费积分→评价/兑换→报表对账”的完整链路，以及取消/跳车、余额不足、并发报名、重复结算、越权等失败链路。

同时完成C8要求的HTTPS/生产配置、三类Push、所有页面离线范围与身份隔离、桌面/移动端视觉和交互、上传安全、每周日凌晨数据库与公私媒体备份、本地4份+COS1份及恢复演练。开发专用预览在生产不可访问；真实浏览器视觉未验证时不得宣称完整视觉验收通过。

本套文档完成后，下一项实施工作是C1；这不是本轮已执行的代码变更。
