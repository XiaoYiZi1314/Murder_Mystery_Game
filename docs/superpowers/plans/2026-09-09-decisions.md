## 使用方式

源文档已明确的要求直接执行；只有影响数据模型、资金口径、权限或验收边界的缺口列在本表。到达“冻结时点”前，由开发者整理可选方案及样本，请需求方确认业务政策，并把确认日期、结论、受影响接口和验收用例写回本文件。当前不需要一次回答全部问题，也不把未涉及的后期问题作为首期阻塞。

工程方案由开发者根据本规划落实；业务政策不能通过测试数据或默认值悄悄决定。冻结后的变更先评估已有记录、迁移、通知及报表影响，不直接覆盖历史事实。

## 资金与履约决策须附带的样本

- **D01：** 一次3人申请获批、重复点击审批、两名员工同时审批；确认最终场次数、报名数和占坑数。
- **D02/D03：** 最低4人/上限6人的场次已有4人；分别包含普通押金和免押金会员，锁车后1人跳车，以及商家取消。逐步列出场次、报名、坑位与押金记录变化。
- **D04：** 两个注册账号、一个3人团队分别用余额/现金/微信结算；增加一笔带小数且有折扣的消费。逐条指定付款主体、应付金额、积分归属与取整结果；如需要混合付款，再增加同一明细拆分支付样本。
- **D05：** 充值500、余额消费200、现金消费100、微信消费150、押金20全退、另一笔押金40全没收。分别列账户余额、消费额、外部收付、押金待退与没收；不能把充值加余额消费当现金收入。
- **D06：** 先累计储值600跨级，再更正其中200，并修改一个等级门槛。分别确认余额、total_topup、等级、通知和原流水可追溯性。
- **D10：** 周/月边界前后两笔消费和跨期冲正，页面报表、汇总API及CSV使用同一时间区间与规则。

样本用于澄清口径，不预设部分退款、混合付款、自动降级等能力一定存在。开发文档中的金额例子只验证相应局部约束，最终断言必须引用冻结结论。

## 工程补齐，可在既定范围内落实

| 工程约定 | 原因与边界 |
| --- | --- |
| 独立booking_requests | 源已有审批流程，报名状态无法表示完整申请生命周期 |
| settlements/items及业务唯一约束 | 区分结束/结算、防止漏记重复记；明细粒度依D04 |
| idempotency_records、event_outbox、可运行消费者 | 报名/资金请求幂等及通知可靠投递；不引入微服务 |
| 公私媒体分离及鉴权读取 | 举报匿名性要求不能与公有Nginx uploads直出冲突 |
| CSRF、统一Actor、敏感命令事务审计 | 在现有Cookie/RBAC方案内落实写请求与权限边界 |
| 数据库ID字符串与页面slug适配 | 保留现有原稿路由，同时避免BIGINT在JSON丢精度 |

这些方案的实现变更需要更新共享协议和相关周期文档，不改变产品功能范围。冻结记录应包含：决策编号、确认日期/人、结论、示例结果、受影响周期/接口、迁移和测试调整。当前全部D项保持“待对应时点确认”，不伪填确认人。
